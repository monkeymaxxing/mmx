# MMX acceptance contracts

MMX's acceptance contracts define correctness for the current pre-alpha build.
The contracts specify the workflows MMX must get right, each workflow's
required outcome, what is out of scope, and when work is complete.
The acceptance contracts are used for completion and review. The
[design plan](design/README.md) owns agreed behavior and remaining work.
The [validation record](validation.md) holds the latest results.

## Acceptance contracts

The workflows in the table below define correctness for the current
pre-alpha build. The linked
[design contracts](design/README.md#design-map)
own the detailed rules. The tests below check the workflows' user-visible
outcomes and inspect server state independently.

| Workflow | Required outcome |
|---|---|
| Reachability confirmation and owed restore | The [execution design](design/execution.md#reachability-confirmation-and-owed-restore) governs acceptance of one module-owned file, and autonomous restoration after lost access, death of the node job worker process, or node restart. Failed restoration retains the recovery data and blocks changes to the module's destination file and replacement of the node runner executable. Human status preserves the original failure and shows the current restore outcome. The foundation has passed `owed_restores.py` on Debian 12 and 13 and Ubuntu 24.04. When the changed node is the controller machine (the same machine ID and boot ID; a clone of its image is an ordinary node), [confirmation also requires new SSH answers from the other inventory nodes that answered before the change](design/execution.md#a-change-on-the-controller-machine-itself), regardless of selection or `--limit`; missing answers withhold every after-change confirmation and appear in the node task failure. The three network file modules and `wireguard_interface` use reachability confirmation and owed restore for file changes; [validation](validation.md) records their guest results. |
| systemd-networkd files | `systemd_networkd_file` manages one whole `.network` or `.netdev` with fixed metadata, reload alone, file-specific journal rejection, fresh reachability confirmation, and autonomous restoration. `systemd_networkd_file` refuses changes to existing devices except identical settings, and refuses removal or renaming while a `.network` file or drop-in refers to the device. `systemd_networkd_file` deletes only unshared virtual devices declared by the source but not the target. Restoration removes only introduced devices. A restored task remains failed and changed. Dryrun writes nothing; missing prerequisites are not checked. `systemd_networkd_files.py` passes on Debian 12 and 13 ([validation](validation.md#systemd-networkd-file-module)). |
| Netplan files | `netplan_file` manages one `.yaml` file in `/etc/netplan`, owned by root with mode `0600`, using only the systemd-networkd renderer. Netplan checks private before-and-after trees before installation; native rejection and unsupported renderers leave the live file unchanged. Changed creation settings for previously declared devices are refused, even when the device is absent. Names owned outside the previous generated tree and changed matches in retained generated network files are refused too. Native diagnostics never expose echoed YAML source lines. Apply alone activates and restores. Cleanup deletes only obsolete virtual devices and clears global addresses only from previously managed links released by removed generated files and now unmanaged. An unchanged file never applies. Dryrun writes nothing, gives no device list, and reports unperformed checks. The shared timer restores bytes and metadata after failed confirmation, death of the node job worker process, or reboot; a restored task stays failed. `netplan_files.py` passes second-card changes, native rejections, virtual-device changes, timer-driven bridge restoration including its port, and the restore after a change that cuts the main card off, also with the worker killed, a restart before the deadline, and a failed restore that an administrator repairs, on Ubuntu 24.04 and 26.04 ([validation](validation.md)). |
| ifupdown files | `ifupdown_interfaces_file` manages `/etc/network/interfaces` or one file directly in `/etc/network/interfaces.d` whose name has only letters, digits, `_`, and `-`, owned by root, with optional `permissions_mode` that otherwise preserves an existing mode and gives a new file `0644`, for the `ifupdown` package of Debian and never ifupdown2; removing the main file is refused when the project loads. A node without ifupdown's programs or an enabled `networking.service` fails a run and is not checked in a dryrun. Before any change, also in dryrun, `ifupdown_interfaces_file` checks the proposed file through standard input. The module refuses syntax errors found by `ifquery` and missing settings found by `ifup --no-act`. The module also refuses a `mapping` stanza or changed `source`, `source-directory`, or `rename` lines. An `interfaces.d` file must be included by the main file's `source` or `source-directory` lines. A change must not take down an interface currently up unless the file lists the interface in `auto` or `allow-hotplug`. The proposed-file refusals apply before any change, including in dryrun. `ifupdown_interfaces_file` takes the changed interfaces down with the saved previous file. The module brings changed interfaces listed in `auto` or `allow-hotplug` up with the new file. The module never touches `lo`. The VLANs on a changed interface that ifupdown lists as up are taken down before it and brought up after it, with the routes their stanzas add. The restore takes them down with the saved proposed file, with `--force`, and brings the previous file's interfaces and those VLANs up, also after a node restart, after `networking.service`. Virtual devices the file declared, such as a VLAN, are gone after removal. The restore data holds interface names and classes only. A restored task remains failed and changed. An unchanged file activates nothing. Dryrun writes nothing and lists the interfaces it would take down and bring up. `ifupdown_interfaces_files.py` covers ifupdown file activation and restoration on Debian 12 and 13 guests switched to ifupdown; [validation](validation.md) records current results. |
| WireGuard interfaces | `wireguard_interface` manages one interface that wg-quick brings up: `/etc/wireguard/<name>.conf`, owned by root with mode `0600`, its private key `/etc/wireguard/<name>.private_key`, and `wg-quick@<name>.service`, enabled and active. The node creates the key once, from 32 random bytes, and the task returns its `public_key` on every run; the private key never appears in a result, the output, saved runs, job records, the journal, or a command line, and the difference for `/etc/wireguard/<name>.conf` shows a note instead of the private key. A file with `PrivateKey`, `SaveConfig = true`, another number of `[Interface]` sections than one, a `[Peer]` without its own `PublicKey`, an allowed IP of two peers, or a setting that wg-quick and wg do not know fails before it reaches the node. The running interface is compared with `/etc/wireguard/<name>.conf` by configuration values rather than text: the key, the listen port, each peer's allowed IPs, keepalive, and whether it has a preshared key, the addresses, a set MTU, the routes that wg-quick adds, and the service. A peer change reloads the service, and the other peers keep their sessions; a changed wg-quick line, address, MTU, missing route, or a keepalive or preshared key that the file no longer sets restarts it; a difference left afterwards fails the task. On a node whose AppArmor policy enforces `wg-quick//ip` without `capability net_bind_service`, as on Ubuntu 26.04, a `ListenPort` below 1024 fails before any change, also in dryrun. Unchanged reruns change nothing; dryrun writes nothing and leaves `public_key` unknown on a node without a key. Configuration file changes, including creation, metadata changes, and removal, use reachability confirmation and an owed restore. Running-state repairs with a matching file do not wait. A restore puts back the previous configuration and service state while keeping the private-key file. `state: absent` removes the private key only after confirmation. An existing private-key file, including a key supplied before MMX's first run, keeps its bytes while MMX corrects its owner, group, and mode to `root:root`, `0600`. `wireguard_interfaces.py` covers the interface workflows; [validation](validation.md#wireguard-interface-module) records guest results. |
| First server and administrator access | `dryrun` or `run` sets up MMX through verified SSH, using keys or separate SSH/sudo credentials, then uses authenticated HTTPS. Removed administrator keys lose access; admitted node jobs continue. A client whose key the account does not list gets one fixed HTTPS refusal that names no account, sudo, or sshd detail; the reason goes to the node's journal. Repeated setup preserves running work. `--connection ssh_only` on `dryrun`, `run`, `run-command`, `check-one-time-playbooks`, or `complete-one-time-playbook` uses SSH for every inventory node and records `connection_used: ssh`; the choice is saved with the run and reused by `resume`, which rejects the option. Other values and commands are command errors (exit 4). Only unreachable HTTPS falls back to verified SSH; a rejected administrator key fails. When HTTPS fails, the run says what MMX saw (the address and, in plain words, what happened) and what the node reports over SSH: whether the node HTTPS API process runs and whether ufw or firewalld is active with no rule that names port 7443. The run names no cause that MMX did not check, records `connection_used: ssh_fallback` with the HTTPS failure and SSH observations, and never opens the port. A replaced server whose new host key OpenSSH trusts is set up again; resume of earlier work on it fails that node. Two inventory names with different addresses that reach one machine with the same machine ID and the same boot ID fail the later name's node before anything is sent, naming both names and saying to check their addresses; two names with the same address and port both run; clones of one image, with one machine ID and their own boot IDs, run as separate nodes. A node runner executable that reports another release version than `mmx`, over HTTPS or SSH, fails the node before anything is sent, naming both versions and the file; a resumed run says to resume with the release that started it. A node with `mmx_runner_download_url` installs only a downloaded runner matching the controller's hash. A node that systemd does not run (no directory `/run/systemd/system`) fails at MMX's first SSH command, over HTTPS setup and `connection: ssh_only` alike and before anything is installed, with one message that the node does not run systemd and that MMX manages only Linux servers that run systemd; a node that systemd runs and whose `/etc/machine-id` is missing gets the advice to run `systemd-machine-id-setup`. |
| Files, templates, and server resources | Apply the declared bytes, metadata, packages, accounts, links, directories, and units. Reject invalid new files before replacement. An unchanged run preserves file contents and avoids unnecessary service actions. `line` replaces the one line `match` (or the exact text) selects, inserts it at the stated position when none does, or removes it with `absent`, keeping the file's other lines, owner, group, and mode; a missing file or more than one selected line changes nothing. A new line goes where the task's one placing setting puts it; a placing pattern that matches no line changes nothing. `edit_file` installs its filter's output the same way, keeping owner, group, and mode, and refuses a filter that would change its own output again, a failing filter, or a missing file without changing anything. Several `line` and `edit_file` edits of one file in a node task block restart or reload the node task block's service once when any changes, including after an attempt that stopped before activation. If a tracked node task's `when` is false at node task block entry, validation and node execution skip argument resolution for the task. If a node task in the block makes the tracked task's `when` true, the tracked task fails with a configuration error. `if_file_exists: keep_existing_content` creates a missing file and afterwards changes only its metadata, never triggering a service restart for file creation or metadata changes. `content_from_node_paths` installs the joined bytes of node files and never shows their text. `backup_original_file_to` copies an existing file once, with its metadata, before MMX first changes it. `symlink.replace_existing_file` replaces a regular file with the link; a directory is never replaced. `directory` with `state: absent` deletes an empty directory. With `also_delete_everything_inside: true`, removal deletes the whole directory tree. `delete_everything_inside_except` deletes every unlisted entry directly inside the directory. If the directory is missing, cleanup creates the directory with the task's owner, group, and mode, as every `directory` task with `state: present` does. No directory deletion follows a symbolic link. A mount point at any path selected for deletion fails the task before deletion starts. A path less than two levels deep is refused. Dryrun deletes nothing. The next run finishes an interrupted deletion. A deletion in a node task block refreshes the node task block's service.  Content writes through `file` and every `download` require `permissions_mode`; known secret content follows the [read-bit acknowledgements](../reference/modules/file.md#files-that-hold-secrets), also in `save_on_controller_machine`. Secret reads in `content` with a literal mode and a missing acknowledgement are refused while loading, before any node job starts; runtime checks cover secret use and modes learned during execution. `line` tasks with `state: present` require one placement setting. Directory cleanup can set metadata on the directory itself. `directory.source` preserves extra node entries by default; `also_delete_entries_not_in_source: true` deletes extra node entries at every depth under the directory-deletion safeguards described above, preserves source-owned entries, reports deletion counts and bounded examples without deleting in dryrun, and reruns unchanged. `also_delete_entries_not_in_source: true` requires `source` and refuses `if_source_directory_is_missing: copy_nothing`, because a missing source would empty the destination. |
| Package sources and patching | A `apt_repository` installs its signing key and, for a private repository, a root-only login file before the deb822 source that names the key; the next installation, version change, or upgrade in the node job containing the `apt_repository` task refreshes indexes; removal deletes the source file, signing key, and login file and keeps installed packages. The repository credentials never appear in the source file or in results. `apt_package` gives every present entry in `packages` a required `name` and `version`; absent entries give only `name`. `apt_package` keeps a package inside a `version` pattern with an apt preferences file that apt honours for every later apt command; a refused version (older without `allow_downgrade`, or matching nothing) writes nothing. `newest_when_first_installed` leaves an installed version alone; `newest_on_every_run` follows upgrades. An apt dryrun reports `not_checked` when current package indexes cannot find a requested package, including when an earlier task would install its source. Real runs refresh indexes first and still fail for a truly missing package; dependency refusals remain failures in dryrun. Every entry and package file is checked before any rule is written; all rules precede one install transaction. A package file must match the entry's name and exact version. The `version` values `newest_when_first_installed` and `newest_on_every_run` remove only MMX's rule and preserve administrator entries. Native simulation refuses removal of any package not explicitly listed for removal unless `also_remove_packages_that_depend_on_these: true`; removal keeps configuration files unless told to purge. A package's scripts may restart a running service but not start a stopped one unless the task allows it. `upgrade_all_packages_within_their_version_rules: true` previews apt's simulated changes without refreshing indexes, then upgrades noninteractively, keeping changed configuration files, optionally autoremoves, and reruns unchanged. `apt_package` restarts nothing itself; a node task block tracking an upgraded package restarts its service once. |
| Packages on Arch Linux | `pacman_package`, an official extra module, keeps the named packages installed or removed through pacman, or upgrades the whole system. Because Arch Linux supports no partial upgrade, every installation refreshes the package databases and upgrades the whole system in the same pacman transaction; a package has no version setting. Installed packages, and absent packages in a removal, are unchanged, and the task then runs only `pacman -Q` and refreshes no database. A run previews the transaction with `--print` against the databases the node has, refuses a group's name and a name that another package provides before it refreshes, then refreshes, previews again, and refuses a name that no repository has before any change; `--print` checks no conflict, so a package that conflicts with an installed one fails in the run, with the packages in conflict named and no package changed; a removal of a group with installed members or of a name that an installed package provides is refused, in a dryrun too; a dryrun refreshes nothing, previews against the databases the node has, and reports a name that those databases lack as not checked. A removal that would also remove packages that depend on the named ones fails before any change, in a dryrun too, unless `also_remove_packages_that_depend_on_these: true`. `upgrade_all_packages: true` is unchanged when pacman has nothing newer after the refresh. The output `changed_packages` lists every package whose version the transaction changed, from `pacman -Q` before and after. Before each command that takes pacman's lock, the task waits up to 60 seconds for `/var/lib/pacman/db.lck` to go, then fails with the reason. Inside a node task block, the installed version of each named package, or its absence, is a tracked input, so a `systemd_service` task restarts its service when the version differs from the one the service loaded. On a node without pacman the task is a missing prerequisite (dryrun: not checked). |
| Packages and repositories on openSUSE | `zypper_package` and `zypper_repository`, official extra modules, keep the named packages installed (each entry with `newest_when_first_installed`, `newest_on_every_run`, or an exact version, installed or updated to and never downgraded) or removed through zypper, update the whole system with `zypper update`, and keep one repository and its signing key. Installed packages, and absent packages in a removal, are unchanged, and the task then runs only reads and refreshes no repository. A run refreshes the repositories, previews with `zypper --dry-run`, and changes with `--no-refresh`; names that zypper would read as a pattern, a path, a capability, a version, or a repository, names that an installed package provides, and a package's name with a version or an architecture (`tree-2.2.1`, `tree.x86_64`) are refused before anything runs, in an installation and in a removal, in a dryrun too; `newest_on_every_run` and `upgrade_all_packages` take only versions from the installed package's vendor, and when zypper says that a newer version is from another vendor the task is unchanged and its reason quotes the remark; zypper's dry run does not see two packages that own one file or a package without a signature, so a run fails with zypper's message and the task is changed; a script of a package that fails (exit code 107) fails the task without another try; a removal that would also remove packages that depend on the named ones fails before any change unless `also_remove_packages_that_depend_on_these: true`; a dryrun refreshes nothing and reports a name the metadata lacks as not checked. Every zypper command of the task runs with `ZYPP_LOCK_TIMEOUT=60`, so zypper waits up to 60 seconds for its lock, for the dry run, the refresh, and the transaction, and the task then fails with zypper's message; a dryrun takes the lock too. The output `changed_packages` lists every package whose version the transaction changed, from `rpm -qa` before and after. Inside a node task block the installed versions of the named packages are tracked inputs. `zypper_repository` requires the signing key (text, or an HTTPS address with its SHA-256) and `repository_metadata_is_signed`, imports the key into rpm before it writes `/etc/zypp/repos.d/NAME.repo` with every setting spelled out, records the key ids that it imported, and removes the repository, those keys from rpm when no other repository's key file holds them (never a key that rpm held before the task), and the key file; another key for a repository replaces the old one in rpm under the same rule; `repository_metadata_is_signed: false` is refused with an `http://` address; package signatures are always checked. On a node without zypper both are a missing prerequisite (dryrun: not checked). |
| Reboot and wait | `shell` and `reboot` name path guards `skip_if_this_path_exists` and `run_only_if_this_path_exists`. Shell resolves relative guards from `run_from_directory` (default `/`); reboot uses `/`. A `reboot` task is only a fleet stage's last task, outside roles, node task blocks, and loops. The `reboot` task reboots only when its guards allow, after the node job's durable result records the boot it leaves; the controller keeps the node's slot until the node answers on a new boot, then the fleet stage succeeds and later fleet stages run on the new boot. A node that does not return within `wait_at_most` fails its fleet stage. Dryrun and a guard that disallows the reboot do not reboot. After loss of the controller process, `status` records a completed reboot and `resume` continues without rebooting again; a node is never rebooted twice for one request. |
| SSH keys and firewall | `authorized_keys` adds a user's keys. Plain listed keys preserve existing key lines with `keys_not_listed: keep` or `keys_not_listed: remove`. Conflicting explicit key options fail before changes unless `replace_options_of_listed_keys: true`. `keys_not_listed: remove` makes the listed keys the complete set. The module can also remove keys. The module uses owner-only `.ssh` metadata and previews keys by fingerprint. An added key gains MMX access. A removed key is refused on the next HTTPS or SSH connection. Keys from `key_files_on_controller_machine` and the `.pub` files of `key_directories_on_controller_machine` on the controller machine join the written keys; the combined keys are saved with the run, so `mmx resume` installs the saved keys; a malformed line, a file without a key, or a repeated key fails validation naming the file and line. A task that only removes keys is unchanged for an account that no longer exists. `ufw` requires an explicit protocol on every rule; `remove` makes installed rules follow the configuration list's order within each rule kind, while `keep` appends new rules. An SSH allowance stays installed during reordering. `ufw` applies incoming, routed, and outgoing rules in order, the three default policies, and the enabled state; `incoming_rules_not_listed: remove`, `routed_rules_not_listed: remove`, and `outgoing_rules_not_listed: remove` remove unlisted rules of that kind and leave the other two kinds alone; outgoing rules match traffic that starts on the node, by destination port, protocol, destination address or network, and outgoing interface; an empty list with `remove` removes all rules of that kind, and `state: absent` removes the listed rules whatever their action; a rule with `from` and no port admits the selected protocols on every port from there, and one with only `incoming_interface` those protocols arriving on that interface. A change leaving the enabled firewall with a blocking incoming default needs an incoming allowance naming sshd's TCP port and admitting the controller machine's SSH source address. The node records the connection kind, source IP, and local IP at node job admission. An SSH connection supplies SSH's source directly; an HTTPS source counts only when HTTPS arrived at the node's inventory IP address. A named `incoming_interface` must hold the node's own inventory IP address; a host-name inventory address cannot qualify. A rule with a source cannot qualify when SSH's source is unknown, including HTTPS arriving at a different node address. The error explains the unknown source and suggests `--connection ssh_only` or a rule without `from`. A preceding `deny` or `reject` rule matching the port, source, and interface fails before changes, in dryrun too. Errors name SSH's source address when known and an example rule to add; outgoing rules never count as admitting SSH. See [The SSH safeguard](../reference/modules/ufw.md#the-ssh-safeguard). `from_inventory_group` on a `ufw` rule makes one rule for each node of the inventory group, so a node that leaves the group loses its rule; a node of the group without the address variable fails validation before any connection; `use_node_address: true` takes each node's inventory `address` instead, which must be an IP address; a rule in a task inside a role reads the playbook run's selected inventory. `ssh_key_pair` makes an account's key pair with the node's `ssh-keygen` only when the private key is missing, owned by the account, and returns the same `public_key` on every later run, which a fleet stage output gives to `authorized_keys` on another node; a missing `.pub` file is written again from the private key, a private key of another type fails, and the private key never appears in output, saved results, job records, or a command line. Unchanged reruns change nothing. |
| Scheduled jobs | `systemd_scheduled_job` requires `run_as_user_account` on every task, including removal; `root` is an ordinary value. It writes a oneshot `<name>.service` and a `<name>.timer` with a marker line, verified with `systemd-analyze verify`, reloads systemd, and leaves the timer enabled and active with the schedule systemd reports as loaded; the service runs the script with `bash -c` exactly as written, as `run_as_user_account`, in `run_from_directory`, with `env`. A `cron_schedule` is translated to systemd's calendar form, and one that restricts both the day of the month and the day of the week fails validation; every schedule is checked with `systemd-analyze calendar` before anything changes. A secret in `env` is only in a root-only environment file, never in the unit, output, or saved runs. Dryrun shows the unit differences, the calendar expression, and the next start time, and changes nothing. A unit edited by hand, an interrupted manager reload, and a timer stopped by hand are put right by the next run. `cron_job` writes `/etc/cron.d/<name>`, root-owned `0644` with a marker line, escaping `%` so that cron runs the command as written, and rejects a secret in `env`; without cron, dryrun reports not checked and a run fails naming the package. For `state: absent`, `systemd_scheduled_job` and `cron_job` remove only files bearing the respective module's marker line. `systemd_scheduled_job` stops and disables the timer before removing files. A present `cron_job` or `systemd_scheduled_job` refuses, in dryrun and in a run, a name whose file already exists without the module's marker line, and `systemd_scheduled_job` also refuses a name that a package's unit has in `/usr/lib/systemd/system` or `/lib/systemd/system`. Unchanged reruns change nothing. |
| A unit that does not start | Every `systemd_service` task requires `state: running`, `stopped`, or `do_not_start_or_stop`; boot activation is `start_at_boot`. `do_not_start_or_stop` still refreshes a running unit after tracked changes and never starts a stopped unit. A unit in systemd's `activating` state, still starting or starting again after a failed start, is not started again: with `state: running`, the task waits for the start and fails if the start fails. Later runs and later attempts of a task that sets `retry` must also wait rather than report an `activating` unit as started. A unit still `activating` immediately after systemd reports a start or restart complete fails the task. When systemd does not start, restart, or reload a unit that a `systemd_service` task asked for, or the unit is not running afterwards, the task's result keeps systemd's message, and its reason gains the last lines that the systemd journal has of the unit from that action alone: at most 10 lines of at most 300 bytes each, 4000 bytes in all. When systemd did not start the unit because a unit that it needs (`Requires=`, `BindsTo=`, `Requisite=`) is not running, the reason names that unit and holds its lines. For a unit with `in_systemd_of_user_account` the account reads its own journal, and root reads the account unit's journal lines by user ID when the account lacks permission. The account's lines for which the journal recorded no unit come under their own heading. A `systemd_service` task tries once unless it sets `retry`, because a start that failed fails again; with `retry`, each try reports the lines of its own action. A journal without unit lines from the requested action, or an unreadable journal, leaves the failure reason unchanged. Reading the journal never fails a task, and a task that read a secret hides the lines with its reason. The timer of a `systemd_scheduled_job` task that systemd does not start or restart reports its lines in the same way. |
| Accounts, access control lists, and capabilities | `user` requires an explicit `create_home_directory` choice and creates an account with its full name, shell, and, when requested, a home directory from the node's skeleton with `useradd`'s permissions, and makes a missing home directory of an existing account when the task asks for one; it never changes an existing home directory. `password_hash` is one whole secret reference: the hash reaches `chpasswd` only on standard input, never a command line, mmx output, saved results, or the journal, and the task's result is suppressed. `only_when_account_has_no_password` keeps a password the person set later; `on_every_run` sets the given password hash again. `password_locked` locks and unlocks password login and keeps the hash. `also_delete_home_directory_and_mail` removes the home directory and mail spool with the account. `group.supplementary_members` with `supplementary_members_not_listed` adds and removes supplementary members and never touches an account whose primary group it is. `file_access_control_list` sets named account and group entries on a path, everything inside it, and as default entries new files inherit, never through a symbolic link; `remove` takes away unlisted entries and `absent` leaves plain permissions. `linux_capability_on_program_file` makes listed capabilities permitted and effective, requires `capabilities_not_listed: remove | keep`, and preserves unlisted flags with `keep`; a later execution of `linux_capability_on_program_file` sets capabilities again if the program file was replaced. A missing tool names its package; dryrun changes nothing and reports a missing tool, path, or account not checked. Unchanged reruns change nothing. |
| Swap, filesystems, and mounts | `swap_file` writes every byte of a swap file of `size` under a temporary name, mode `0600` and owned by root, gives it its swap signature, renames it into place, switches it on, and adds its `/etc/fstab` line; every step is found by inspection, so the run after an interrupted one does only the missing steps and deletes the unfinished file; a swap file of another size is switched off, written again, and switched on; a file at the path without a swap signature is never replaced or deleted; `absent` switches it off, removes its line, and deletes it. `create_filesystem_on_empty_device` probes the device with `wipefs --no-act` and creates the filesystem only when it finds no signature of any kind, is unchanged when it finds only the requested type, and otherwise fails naming every signature (another filesystem, swap, a partition table, LVM, RAID, LUKS), in dryrun too, never passing a force option and leaving the device as it was; a device without a signature that the kernel reports in use fails too. `fstab_mount` requires explicit mount options and boot check choices and owns the one `/etc/fstab` line with its mount point and leaves every other line and comment untouched; `/etc/fstab` is replaced atomically only after `findmnt --verify` accepts the new file, and systemd reloads it; the path is mounted when nothing is, remounted when the listed options change or the live mount's flags differ from them, and a live mount of another source or type fails without a change; `unmounted_and_removed_from_fstab` unmounts and removes the line, keeping the directory, and a busy mount fails with the system's message. A missing program names its package; dryrun changes nothing and reports a missing program, directory, device, or mount point not checked. Unchanged reruns change nothing. |
| Disk partitions | `create_partitions_on_empty_disk`, an official extra module, writes a GPT partition table with `sfdisk` only on a whole disk. Review related paths together: stopping, Ctrl-C, and loss of the controller
process or node job worker process during a node task block's activation
and cleanup; uncertain submission, status collection, resume, and
node-history expiry of the same node job; secret values through outputs,
exports, differences, results, and resume; setup of the node runner
executable beside admitted node jobs; and HTTPS fallback beside identity
or key rejection. The
[acceptance checks](#acceptance-checks) map the workflows in the table above
to focused tests and real-system workflows.

The contracts describe outcomes for the typical deployment: one administrator
or a small team with full root, working directly or through a coding agent or
CI, running a controller process against one to a few hundred servers,
rarely more. Administrators and the people the administrators grant access
are trusted.
Guarding servers against misuse by administrators or authorized people is
out of scope. MMX must
also stay fast at the 10,000-node test fleet, measured in
[performance](../reference/performance.md). Scale work that keeps MMX fast at 10,000
nodes belongs in the code, but findings are judged against the typical
deployment. Absolute words in
the contracts state the outcome in ordinary operation, not a promise about
every possible ordering of concurrent actions.

The review rules below serve MMX's goals: it works, it is secure, it is fast,
and it is easy to use. Judge a finding by whether the finding threatens
MMX's goals in practice, not by whether some sentence can be quoted against
the code. Work that serves none of MMX's goals is a side quest. Leave the
work out.

A correctness blocker needs a concrete violation of an acceptance contract
in a supported workflow. Evidence must be a failing test or a demonstrable
code path from specific inputs and state to a wrong outcome.
The typical deployment described above must plausibly encounter the
violation in ordinary operation. The violation must cause at least one
of the following outcomes:

- Leave a server in the wrong state.
- Disrupt a running service with an action the run should not take, such as
  an unnecessary restart or drain, or any change from a dryrun.
- Report a wrong outcome or exit code.
- Lose or leak data or secrets.
- Hide a failure.
- Let an unauthorized party act.
- Stop a supported workflow.

A scenario that needs several unusual conditions at once or precise timing
is not a blocker. A scenario causing only a delay or a slightly wrong
message is not a blocker. Fix a blocker with a test that proves the
contract. Verify related paths before closing the blocker.

Every fix adds code the next reader must follow, and MMX stays small only if
most findings are dropped. Record an improvement only when
the typical deployment plausibly encounters the problem in ordinary use,
the problem causes a real loss, and the fix is small. Drop everything else.
Design text the code does not implement, a
mistake in the user's own configuration that MMX already makes visible, and a
cosmetic difference are not findings: correct the text or leave the text
unchanged. Prefer fixes that remove code, and add no mechanism for a case
that neither the typical deployment nor the 10,000-node test fleet will
meet.

A scoped change is complete when the agreed outcome is implemented,
affected code and real-system workflow tests pass, and current documentation
matches the implementation.
An acceptance pass is complete when the applicable
[acceptance checks](#acceptance-checks) pass, the
implementation and guides agree, and no known correctness blocker remains.
Report the commands, results, and unverified boundaries, then stop.
Reopen the acceptance pass for a concrete failing contract, a changed
requirement, or a code change affecting a contract.

Ordinary failures are in scope: rejected new files and credentials, failed
tasks, unreachable nodes and endpoints, termination of the controller
process and node job worker process, reboot, interrupted setup and uploads,
and a second controller targeting the same node. Out of scope for this build:
distributions beyond Debian and Ubuntu, package
managers beyond apt, changes to existing accounts' numeric user IDs or
groups' numeric group IDs, full-disk/interrupted-write and broader
competing-controller fault matrices, exhaustive fault combinations, large-scale
comparisons, and cross-release tests of resume and node setup. The
excluded categories require separately agreed work. The exclusions for
the current build do not relax input validation,
credential handling, data-loss protection, or bounded recovery. The
[test plan](design/development.md#automated-code-and-workflow-tests)
separates current checks from deferred matrices. Existing development code and
disposable state create no compatibility obligation beyond the [release
compatibility promises](design/README.md#compatibility-between-releases).
The saved controller-machine state in `.mmx/` may be discarded. A new node
runner executable must read command and service records from every earlier
release.
